# 1.5.2 皮肤动画与预处理发布审阅

本次基于 1.5.1 主线 `8437bce`，修复自定义背景在二级 Activity 和面板交接时短暂退回主题色的问题，增加默认关闭的屏幕四角适配，并纳入同轮的异步 Mica 预处理与源码契约索引优化。具体发布提交及远端结果由 Release 的 `VERIFICATION_1.5.2.json` 绑定。

## 原因与实现

柔光会话恢复时原本释放了已准备背景，新页面也只能等待自己的异步解码，因此会先画默认主题色，再渐显用户背景。新实现为每种材质保留一对已发布的背景像素，按完整配色、背景配置、窗口尺寸、密度及光学档位精确匹配。恢复及新页面命中时立即使用相同像素，不重复渐显；Liquid 的 Shader 与矩阵仍按会话独立创建，首次加载的原有渐显保留。

冷背景的形变在透明准备态有界等待就绪，最多 250 ms。它不在主线程解码，不改变入场时长、返回手势及插值；旧代次、取消和销毁不能重新启动页面。普通背景及命中缓存的路径不增加等待。

`ContainerMorphHost.followScreenCorners` 默认 `false`；显式启用后，背景、表面及内容按 API 31+ 当前窗口的四个半径连续插值和裁剪。缺少系统数据或未覆盖对应角时沿用原展开几何。公开构造不变，旧系统平台类型继续放在 `ScreenCornersApi31` 隔离类中。真机检查发现系统兼容桥会重入一份不带圆角的数据，现于系统处理返回后使用外层完整输入更新，避免有效四角被覆盖。

面板标题的共享颜色所有权原先已能追踪持有者，但实际绘制仍独立使用单个代理的权重。现在绘制和释放均使用合并后的权重；有其他持有者时不提前恢复文字，最后一个释放才归还原始 `ColorStateList`。来源 View 的 alpha 及涟漪不被隐藏。

## 性能与生命周期 review

- 缓存只持有已发布像素和不可变匹配键，不持有 Activity、View、Context 或渲染会话。每种材质最多一对、4 MiB，两种合计最多 8 MiB，不随页面数增长。Liquid 单个缓冲原有 2 MiB 上限、采样尺寸及光学配方保留。首轮真机暴露了把一对误按单缓冲预算计算的问题，已按完整双缓冲上限修正；没有降低图片质量来满足缓存。
- 已发布像素不强制 recycle，缓存驱逐只释放引用；低内存与显式图形释放清空缓存。该预算不代表活动页面、整个进程或 GPU 内存上限。
- 圆角坐标仅在 insets／尺寸更新时读取；帧路径复用 Path、矩形及数组，均匀四角保留原来的圆角矩形路径。
- 新 `LumenMicaPreparer` 为所有者独立的可关闭 worker：只保留一个正在处理、一个最新待处理和一个最新待交付结果。输入惰性获取并在后台 finally 回收，已交付输出不回收；主线程 Handler 交付不依赖 View 挂载。既有同步借用 API 与 Mica 配方不变。
- Motion 契约只在单次测试 JVM 内复用源码快照、文件名索引、词法掩码及已验证声明。完整源码仍是 Gradle Test 输入；缺失与歧义仍失败。此前隔离探针的纯注释变化和负向违规检查见 [同轮预处理阶段记录](ASYNC_PREPARATION_REVIEW_2026_10_23.md)，其中“未发布”属于当时状态。
- 未增加生产依赖、放宽 Lint、增加基线、关闭测试或改变四版本发布门禁。新增可选 API 按用户明确指定使用 1.5.2，编号例外记于 `VERSIONING.md`；契约版本 1、持久化协议与 minSdk 27 保持兼容。

## 设备复现与回归

在 PMA110 / API 37 上，以未修改的 `8437bce` 运行时加同一条新回归用例复现：柔光浅色页面恢复后，首个检查点由自定义背景像素变为默认主题色，断言失败；安装和 runner 均正常。原始失败单独保留，没有重试覆盖。

修正后的独立 sample 包通过 25 项定向真机测试，0 失败、0 错误、0 跳过：两种材质和浅深配色的恢复／新会话首帧、居中／锚定／气泡／覆盖子面板的开合及文字恢复、真实二级 Activity 往返、非对称四角裁剪与关闭恢复、冷背景等待、异步预处理与已有 Mica、分页和面板几何回归。拉回的 app/test base.apk 均与本轮 bundle 哈希相同；原 sample、test 和 BIL 模块的安装路径保持。

使用程序生成的测试图片，未将用户图片加入仓库。对两种材质的浅色／深色入场、展开、退场，保留窗口及包含底页的系统合成截图共 24 张并复核。它们验证所检查帧的皮肤与角形连续性，不作为全程逐帧、帧时间、功耗或多厂商等价性的证明。

设备副本仅在固定主线加本次源码后使用独立 applicationId；其基线 SHA 与未提交补丁哈希分别记录，没有把基线 SHA 声称为包含补丁的发布提交。最终发布以标签提交下的完整远端门禁为准。

## 发布边界

首轮 main 的 CI 与 API 27／31／34 全量冒烟通过，API 33 ATD 在真实二级页用例中设备连接中断，runner 只完成 15／181 项且没有终态，严格门禁正确判为失败。原始 instrumentation、logcat、主机内存与作业日志保留，没有断言失败或 OOM 记录。额外的整屏合成截图现改为显式本地取证选项；四版本仍执行全部产品断言和窗口 PixelCopy。新加的冷背景用例还检查首次报告 ready 的那一帧确实已经显示自定义像素。没有以重试、跳过用例或放宽阈值处理该故障，最终提交须重新完成全部门禁。

补充冷首帧用例并取消门禁额外整屏取证后，API 33 ATD 仍在相同的真实窗口用例中掉线：完成 15／182 项、adb 返回 255、没有 runner 终态；主机可用内存约 11.6 GiB，未见应用断言或 OOM。该记录表明额外整屏截图并非充分解释，故将 API 33 改用同版本 `google_apis` 标准图形镜像，与 API 31／34 保持完整窗口合成环境，全部 182 项、窗口 PixelCopy、GPU 像素和协议检查保留。发布脚本要求的成功作业名同步更新，旧 ATD 结果不能满足新门禁。[Android 官方说明](https://developer.android.com/studio/test/managed-devices)指出 ATD 默认关闭硬件渲染，依赖硬件渲染的截图测试不受支持；这里使用标准镜像承担真实图形验证的资源开销，没有降低视觉质量或删去用例。

标准 API 33 镜像中，额外动画窗口回读仍在同一用例中导致连接中断，其他三版本完整通过；这说明仅更换镜像也不足以解释并解决故障。该用例的窗口及整屏 PNG 写出统一移到显式本地取证选项：它们没有颜色数值断言，属于额外诊断输出。必测的真实 Activity 往返、亮暗配置、圆角开关、展开／关闭及文字恢复保留，并增加展开后真实背景层的自定义像素断言；同组恢复／首帧／冷就绪颜色断言和既有窗口 PixelCopy／GPU 像素契约均保留。PMA110 的可选窗口与整屏取证已单独通过并核对实际安装包哈希，锁屏造成的那次入口不可见失败也单独保留。最终图形层故障归因仍受上述日志范围限制，最终源码必须重新通过四版本完整用例及物理设备检查。

接入审阅另发现来源模块保留了自己的部分材质 renderer，因此公开 `LumenPreparedBackdropCache` 作为薄适配入口，并让就绪接口在形变前显式准备完整皮肤首帧。宿主真机像素检查进一步捕获其原生分辨率显示图超出默认 4 MiB 缓存预算的问题；模块原有显示上限是 8MP，而非内置材质的采样图。缓存提供显式预算构造，上限按现有 8MP ARGB 显示图加 2 MiB 光学图确定为 34 MiB，每实例仍限一对；模块按原有策略计算预算，两种实例合计最多 68 MiB，只共享既有像素，不新增同尺寸像素副本，低内存与进程图形释放清空引用。内置材质默认 4 MiB／合计 8 MiB 保持。新增行为检查覆盖宿主预算、单条目替换、越界拒绝及非法预算；既有默认越界、淘汰、关闭和压力释放断言保留。宿主缓存实例的预算单独计入，没有通过缩小显示图满足预算。

发布前必须由精确 main 提交通过 CI 与 API 27／31／33／34 全量冒烟。库附件先上传到匹配的 draft，再公开发布；Demo 从不可变 1.5.2 标签构建，四系统使用同一对 APK，全部通过才附到 Release。九模块 JitPack 公开 POM 与提交一致性及所有附件摘要由最终验证脚本核对。

远端作业链接、提交、APK 与库哈希以 `VERIFICATION_1.5.2.json` 和 `SHA256SUMS.txt` 为准。本审阅不预先宣称远端发布已完成；PMA110 的定向结果不外推其他厂商，也不宣称本轮已测得 FPS、RSS 或功耗改善。
